# RainReady Data Source Register

This document records the candidate data sources for the MVP. Published refresh intervals below come from the source pages; they are not guarantees of end-to-end delivery latency. Before coding an adapter, inspect the current API specification and save a redacted sample response in the repository. Never commit API keys, AWS credentials, or participant contact details.

## Polling and freshness policy

Event checks retrieve feeds on demand; RainReady does not run a background poller. The upstream refresh cadence is not a guarantee that a newly published forecast is available at every check. The frontend's primary and backup checks send the identical saved event date/time, so both are matched to the same forecast window. Do not compare if the exact period boundaries differ or either assessment is stale/unavailable. The two-hour and 24-hour feeds are not combined into a fabricated continuous forecast: select the single published period covering the start. A saved activity's duration is not modelled. If no period covers the start, show no score and ask the organiser to recheck later or decide manually.

When operating any optional polling or cache refresh outside the current on-demand prototype, do not poll faster than the source's published cadence unless the API specification explicitly recommends otherwise: 2-hour forecast 30 min; 24-hour forecast 6 h; 4-day forecast 12 h; rainfall 5 min. Retrieve PSI on demand and retain its observation/update time; RainReady marks it stale after 90 minutes as a prototype display assumption. For lightning, use the documented 2-minute display cadence only if the API spec and response behavior support polling, while clearly showing the observation/source timestamp and measured retrieval time. Do not imply that polling more often makes upstream data fresher.

The 2–4-day estimate uses RainReady's prototype forecast-severity mapping, a prototype band for the forecast daily high temperature, and the event sensitivity factor; current rainfall, unvalidated history and future PSI are excluded. The daily weather-concern input is the higher of the mapped forecast text and temperature band. Numeric wind severity is excluded if a validated unit is unavailable. Advice rules can reference the daily forecast summary, supplied temperature range, activity type and sensitivity. These are planning prompts and prototype assumptions, not NEA safety or medical thresholds. Show the source timestamp and repeat that the outlook is Singapore-wide and daily. Do not claim exact event-time risk or recommend a venue comparison from this feed.

Store both the source observation/update time and RainReady's retrieval time. Show a visible freshness state (Current, Delayed, or Unavailable) based on a documented threshold. When a request fails, retain the last successful response with its original timestamp and mark it stale; never silently present cached information as live. If no valid cached response exists, show “data unavailable” and avoid generating a confident weather-based recommendation. Keep manual organiser decisions available and record them separately from automated assessments.

## Safety and interpretation

### Implemented processing in the prototype

- For the saved event start, select the covering NEA two-hour local-area forecast period; if it does not cover the start, select the covering 24-hour regional period. Never use a current forecast merely because it is the newest response if its valid time does not include the event start.
- Map each selected official forecast label to a RainReady 0–100 weather-severity input. Match specific labels before broad labels (for example, `Partly Cloudy` before `Cloudy`). These are prototype mappings, not NEA hazard thresholds.
- Map organiser-selected event sensitivity (`low`/`medium`/`high`) to a separate 0–100 contribution. For an event-time assessment, exclude latest five-minute rainfall and historical probability because they are not validated, aligned predictions for the scheduled time; renormalise forecast/sensitivity base weights over the remaining components. Keep the current-snapshot mode clearly labelled if called without an event time.
- Only compare main and backup venue scores when both are current and refer to the exact same forecast start/end window. The comparison is a weather heuristic and does not validate the backup venue operationally.
- Keep PSI separate: use NEA's published category bands for user-facing advice and an optional owner-facing ordinal display (0/25/50/75/100). Do not add this 24-hour regional reading to the local current-weather score without a validated time/location alignment and justified calibration.
- Do not use entropy weighting for the current prototype. Input dispersion alone does not establish which variable predicts event interruption. First collect a suitable event-time dataset and predefine an outcome label and validation method.

- Normal weather risk is decision support, not an official warning or a guarantee that an activity is safe.
- Use “lightning observed near this event” only if the live fields and an explicitly chosen radius/time window support it. State the radius, time window, feed timestamp, and uncertainty in the UI.
- A lightning observation must not be labelled an “official lightning warning.” Any mandatory stop/shelter instruction must be tied to a separately verified institutional safety policy or a manually confirmed official warning. A human organiser records pause/resume decisions; the system never automatically resumes an event.
- Keep alert thresholds configurable and document them as project assumptions, not NEA standards.

## Official source notes

The source pages identify NEA as the agency for the weather, rainfall, lightning, and historical-rainfall datasets. The rainfall page warns that observations may have technical gaps, may later be corrected, and may be affected by local conditions. The lightning page describes the feed as MSS Lightning Detection System data and explicitly notes transmission delay, location error, possible missed/false detections, and gaps. The historical rainfall page says its records may be missing and are not quality-controlled for official climate use. OneMap Search requires a valid authorization token; see the [Search API](https://www.onemap.gov.sg/apidocs/search) and [token authentication documentation](https://www.onemap.gov.sg/apidocs/authentication).
